## One-click setup diagnosis

The user's touchpad left click appeared to open Settings. Inspection showed the primary-click handler reached the voice action; its readiness guard reopened Settings because the reply voice key was unavailable in Windows Credential Manager and no reply voice was selected. Deepgram reported ready, and the saved model remained GPT‑6.1 Terra / Medium. This is not a successful voice turn or proof of a touchpad mapping defect.

The UI incorrectly used “Stored in your OS keychain” as the placeholder when no voice key was configured. A failed voice-catalog request also left “Loading voices…” displayed, with the actual error buried below the settings sections. The fixes use a truthful placeholder, identify the missing requirement, replace the loading status on failure, and keep errors beside Save. The user has been asked to enter only the missing reply-service key and select a voice locally.

The frontend release build, all 14 orb unit tests, all 7 static accessibility contracts and WASM Clippy with warnings denied passed. A Windows x64 release executable and NSIS bundle built successfully. The new error presentation and full voice turn still need native Windows validation.

## Remote microphone and early-stop investigation

Windows App's saved connection had microphone forwarding off. With the user's explicit approval it was enabled, the session reconnected, and Windows Sound → Recording listed Remote Audio as the default input. macOS Privacy & Security also shows Windows App microphone access enabled. No voice turn has passed on Windows.

After local voice setup, activation stopped after roughly 1.1 seconds. The old message combined device failures with queue overflow. Splitting these paths and testing on Windows confirmed the **device-failure callback**, not the queue-overflow path. Increasing bounded queue headroom did not resolve the early stop. Two no-speech trials still stopped early; neither is counted as voice acceptance.

The investigation also exposed an error-reporting race: the capture-cancel event can clear the frontend's manual-capture flag before polling surfaces the native error. The fix publishes the failure before cancellation, preserves the error through frontend cleanup, and includes a bounded native error description. The original 320 ms input queue is now bounded at two seconds to tolerate batched callbacks without adding a deliberate wait; overflow still rejects the capture rather than silently dropping speech. This hardening is not claimed as the device-failure fix.

Three focused, non-audio regression tests pass: a one-second stereo callback with a partial packet, bounded overflow, and error preservation through cancellation cleanup. Native and WASM Clippy with warnings denied, the frontend release build, seven static accessibility contracts and the Windows x64 release build pass. The diagnostic changes have not yet been installed or acoustically verified on Windows.

The user deferred all audio testing until tomorrow. Mac QA was quit and Windows Settings was left open with wake mode off. The next step is to install the diagnostic candidate and inspect the underlying Windows stream error before another spoken acceptance attempt. No demo recorder was used.
