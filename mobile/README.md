# notdot mobile (prototype)

Status: **private prototype on a draft branch.** Native SwiftUI (iOS) and Jetpack Compose (Android) shells over a shared Rust core. Not a release. No store submission, signing account or paid service is used.

The conversation is voice-only. Text fields exist only for setup (pairing). There is no chat composer.

## Layout

| Path | What it is |
| --- | --- |
| `crates/notdot-orb` | Canonical orb shader (`orb.frag`), state/motion (`visual_state.rs`), `theme.rs` and `contract.rs`, shared with the desktop. Golden vectors and golden frames are in `fixtures/`. |
| `crates/notdot-orb-gen` | Generates platform shaders from the canonical source (Android: verbatim GLSL; iOS: Metal via naga) and lints for hand copies. |
| `crates/notdot-link` | Pairing, typed `link/1` protocol and Iroh transport; `attest` verifies Android key attestation and Apple App Attest for step-up keys. `examples/desktop_sim.rs` is a test-only desktop that approves automatically. |
| `crates/notdot-wake-kws` | The desktop's sherpa-onnx keyword spotter and the Whisper backup's utterance cutting (`Utterances`), shared with mobile. |
| `crates/notdot-wake-runtime` | The desktop's Whisper decode rules (`engine`), used unchanged by the mobile backup. |
| `crates/notdot-mobile-core` | UniFFI layer: orb engine, hands-free session lifecycle, wake engine (spotter + Whisper backup), phone link with restorable identity. |
| `mobile/rust` | Builds the app library. Its own lockfile pins `libc` 0.2.189 (see below); `scripts/check_mobile_lock.py` keeps every other package equal to the desktop lock. |
| `mobile/ios` | SwiftUI app, Live Activity extension, unit tests. The Xcode project is generated by `scripts/generate_project.py`. |
| `mobile/android` | Compose app, microphone foreground service, JVM and instrumented tests. |
| `deploy/relay` | Local proof of concept: iroh-relay behind a TLS reverse proxy. Not deployed. |

Generated code (Swift/Kotlin bindings, static/shared libraries, Metal sources) is written to ignored build folders and is never committed.

## Build and test (all silent)

Unattended tests never play audio and never open a microphone. The iOS test scheme passes `-NotdotSilentTest YES`. Android instrumented tests set silent mode, and the emulator runs with `-no-audio`.

```bash
cargo test -p notdot-orb -p notdot-orb-gen -p notdot-wake-kws -p notdot-mobile-core
cargo test -p notdot-link --features test-relay
```

```bash
python3 mobile/ios/scripts/generate_project.py
```

```bash
cd mobile/ios && xcodebuild -project Notdot.xcodeproj -scheme Notdot -destination 'platform=iOS Simulator,name=iPhone 17' CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=- test
```

The simulator Keychain needs a signed app, so tests use ad-hoc "sign to run locally" signing (`CODE_SIGN_IDENTITY=-`). It uses no certificate and does not touch the Mac's keychain.

Both apps build with the Whisper backup by default. Set `NOTDOT_WHISPER=0` for `build-core.sh` (and `embed-native.sh` on iOS), or pass `-PnotdotWhisper=false` to Gradle, to build the spotter alone. whisper.cpp builds with CMake; on Android it uses CMake's NDK support. On a macOS host, whisper-rs-sys 0.15 picks BLAS from the host rather than the target, so the Android script links an empty `ggml-blas` stub there; Linux hosts need nothing extra.

```bash
mobile/android/scripts/build-core.sh debug
```

```bash
cd mobile/android && ./gradlew :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest
```

```bash
emulator -avd <avd> -no-audio -no-window -gpu swiftshader_indirect
```

To include the end-to-end link tests, run `cargo run -p notdot-link --features test-relay --example desktop_sim -- <qr-file> [bind-ip]` on the host. Then pass the code to the tests: on iOS with `TEST_RUNNER_NOTDOT_TEST_QR_FILE=<qr-file>`; on Android with `adb shell am instrument -w -e notdotQr "$(cat <qr-file>)" dev.notdot.mobile.prototype.test/androidx.test.runner.AndroidJUnitRunner`. Use the host's LAN address as `bind-ip` for an emulator. The simulator desktop approves every request: use it in tests only.

None of this is evidence of behaviour on a physical phone. The only acoustic evidence is from a Mac's own speakers and microphone.

App microphone capture could not be exercised on this Mac. With Xcode 27, the iOS simulator's host audio input is never authorised: no Simulator app or helper declares microphone use, so macOS shows no prompt, and the app's audio unit aborts with an RPC timeout. The Android emulator hung when host audio was enabled. App microphone evidence must come from devices; debug builds include an unattended auto-start hook for that (`-NotdotAutoStart YES` on iOS; the `notdotAutoStart` intent extra on Android).

## Still open (hypotheses and hardware-only gates)

- **W1, wake on device:** the apps now run the desktop's full detector: the keyword spotter plus the same Whisper backup (model `ggml-tiny.en-q5_1`, decode rules and utterance cutting shared with the desktop). Offline it matches the desktop on every corpus and synthetic clip, including quiet speech the spotter misses. Still unmeasured, and only measurable on phones: accuracy and false wakes per hour in real rooms, CPU and battery per hour, and decode time. Risks to check first:
  - **Decode time.** The backup decodes every utterance of speech it hears (about 41 a minute of continuous speech on the synthetic set). On the Android emulator a decode averaged 1.5 s and peaked at 2.0 s of the 3 s budget; a slow phone may time out or fall behind. If so, options are fewer threads or a lower duty cycle, a smaller model, or decoding only near-misses of the spotter; each changes recall and needs measuring.
  - **Budget overrun under load.** The 3 s budget and cancellation both act through Whisper's abort callback, which runs between processing steps. On a contended 4-core CI runner (several engines decoding at once) a decode took 3.7 s and a drop 3.8 s. Tests now run one engine at a time, as a phone does, but a slow or busy phone may still overrun by one step; check `decode_ms_max` on the device.
  - **Queued utterances (fixed offline, unmeasured on phones).** Utterances used to be held while a decode ran and kept growing, so on a slow decoder unrelated speech was joined to a following "Hey Ava", which the address rule rejects. They now end at their pause regardless and wait (at most two, oldest dropped first and counted in `dropped`). On a phone that cannot keep up, a wake phrase can therefore be decoded up to about two decodes late, or dropped under sustained overload; `dropped` and decode times in the debug log show whether that happens. The desktop shares the change (its wake tests pass).
  - **Memory and size.** On the host, a spotter-only engine added 72.5 MiB of resident memory and a full engine 84.9 MiB (its own spotter plus the backup). A release arm64 Android build grows by 2.5 MB of native code (1.2 MB in the core library, 1.3 MB for `libc++_shared.so`) plus the 32 MB model, which is stored uncompressed in the APK and copied once to app storage.
  - Spotter-only recall is CPU-sensitive (the x86_64 CI runner missed one clip); the backup covers it offline. On iOS the sherpa library is embedded as `SherpaOnnxC.framework`, the form sherpa-onnx ships; App Store packaging of it is untested.
- **W2 / W2-A, long hands-free sessions:** behaviour through lock, Doze and OEM battery managers on real devices; battery drain per hour; App Review and Play review of a long user-started session.
- **W3–W5:** starting from an Action button, Control, Siri, widget or tile while suspended or after a force-quit; pre-emption by calls and assistants on hardware.
- **Keys:** the phone's link identity (an Ed25519 key) is created when the user starts pairing and kept this-device-only: in the Keychain on iOS (readable after first unlock, no access control, so no prompt), and on Android in no-backup files sealed by an AES-GCM key held in the Keystore (no user authentication). It is not hardware-bound: the 32 bytes pass through app memory when stored and restored. If the desktop removes the phone, the core reports it unpaired and the apps delete the identity, record and step-up key. On Android, files that cannot be unsealed are replaced the next time the user pairs, rather than blocking pairing.
- **Step-up and attestation:** the step-up key is set up from the sensitive-actions screen, not at pairing. The desktop issues a single-use enrolment challenge (5 min) and verifies platform evidence itself (`crates/notdot-link/src/attest`); nothing the phone says about its hardware is trusted, and an unconfigured desktop accepts nothing. Each sensitive action then needs a live owner grant at the desktop, a fresh 60 s challenge bound to the operation, and a biometric signature; setting up a new key ends the grant. Before every challenge and action the enrolment is rechecked against the current policy and Google's latest status list: a key whose chain was revoked later, whose app or signer is no longer allowed, or whose list has gone stale is forgotten, and the phone is told why. If the reply to set-up is lost, the phone keeps the new key pending and settles it from the key fingerprint the computer reports.
  - **Android:** the key (P-256, StrongBox first, strong biometric per signature, invalidated by new enrolment) is created with the challenge, and its Keystore attestation chain is the evidence. The desktop requires Google's root (pinned keys from `android.googleapis.com/attestation/root`), every certificate current and off Google's status list (fetched by the desktop, at most 48 h old), TEE or StrongBox for both levels, the exact key properties, a locked bootloader with verified boot, and an allowed package and signing certificate. Not verified here: the desktop app does not yet fetch the status list or hold a policy (the desktop integration of the link is still `desktop_sim`); a device whose factory certificates have expired is refused; chains signed with algorithms other than RSA and ECDSA are refused.
  - **iOS: what is and is not attested.** Apple offers no attestation for an arbitrary Secure Enclave key. The step-up key is a Secure Enclave key (biometryCurrentSet). App Attest attests a different key, held by `DCAppAttestService`, as belonging to a genuine instance of this app on Apple hardware. The app binds the step-up public key into the App Attest client data, and every action carries both the step-up signature and an App Attest assertion (counter must rise). So the desktop knows the genuine app vouched for the step-up key; that the key is in the Secure Enclave behind biometrics is the app's behaviour, not an Apple attestation. The desktop records this as "app attested".
  - **iOS blocker (owner action and payment):** App Attest needs the `com.apple.developer.devicecheck.appattest-environment` entitlement on an App ID registered by an Apple Developer Program team, which is not authorised. Until then every iPhone build reports App Attest unavailable and sensitive actions stay off. After enrolment: add the entitlement, put the team ID and bundle ID in the desktop policy, and record the `apple_validation_category_01` value a TestFlight build reports (Apple documents only `1` in its sample) before accepting it. Apple's receipt (fraud metric) is stored but not checked: that needs server-to-server access to Apple.
  - **Not proven on hardware:** key creation in StrongBox, TEE or Secure Enclave; the biometric prompt; a genuine attestation accepted by a desktop; App Attest attestation and assertions on an iPhone; invalidation after a new enrolment. The verifiers are tested on genuine platform data from Apple and Google, but not on evidence from the owner's own phones.
- **Relay deployment:** a recommendation only (see `deploy/relay/README.md`); needs owner approval.

## iOS: two lifetimes, kept separate

- **Audio session.** With the `audio` background mode, recording with `record`/`playAndRecord` continues when the app moves to the background, for example when the screen locks. Apple documents no time limit for this.
- **Live Activity.** It can be active for up to eight hours, and then the system ends it. It may stay on the Lock Screen for up to four more hours.
- **AudioRecordingIntent** (iOS 18). Apple says the app must start a Live Activity when recording begins and keep it active while recording, and that recording stops if no Live Activity is started. Apple does not say what happens to the recording when the Live Activity reaches its limit.
- **notdot's rule.** A hands-free session is tied to its visible Live Activity. When that ends, for any reason, the session ends. The eight-hour maximum is therefore a product rule derived from the Live Activity limit, not an audio-session limit. Whether recording would continue past a Live Activity's end is undocumented and untested; it is not relied on.

## Real-device test plans (nothing sent or enrolled yet)

**Android: Motorola phone on Android 14 (owner's device)**
1. Enable developer options and USB debugging; connect; check `adb devices`.
2. Build with `mobile/android/scripts/build-core.sh debug && ./gradlew :app:assembleDebug :app:assembleDebugAndroidTest`. It is debug-signed with the local debug key, so no Play account is needed.
3. Install both APKs with `adb install -r -t`. Run the instrumented tests as above. The silent tests need no audio.
4. Audible and acoustic checks wait until the owner lifts the night-time restriction, and need the owner present: wake from across a room, during playback and with media playing; session through screen-off and Doze (1 h and 8 h); Motorola battery settings; a call during a session; reboot or force-stop recovery with one tap. Record drain per hour.
5. Wake measurements (W1): start a session with the debug `notdotAutoStart` extra after `adb shell pm grant dev.notdot.mobile.prototype android.permission.RECORD_AUDIO`, then read `adb logcat -s notdot.voice`. Once a second it logs input level and the backup's state, decode count, wakes, failures and decode time (never audio or text). Compare `decode_ms_max` with the 3 s budget and decode time per minute with the host's 6.6 s; repeat with `-PnotdotWhisper=false` for the spotter alone.
6. Step-up and attestation (silent; needs the owner's fingerprint): with a screen lock and fingerprint set up and the phone online once (attestation certificates come from Google), run `desktop_sim` with `NOTDOT_SIM_ANDROID_APP=dev.notdot.mobile.prototype:<debug signing certificate SHA-256>` and `NOTDOT_SIM_STATUS_LIST=<freshly fetched status list>` (values from the local machine, never committed), pair, then use "Sensitive actions" → "Set up sensitive actions". Expect the desktop log to show `android_strong_box` or `android_trusted_environment`, not `test_only`. Unlike the emulators, a retail phone's chain should verify; if it is refused, the reason is in the app. Then rerun `desktop_sim` with `NOTDOT_SIM_GRANT_MINUTES=10` as well (it stands in for the owner's grant), set up again, and use "Erase assistant memories": cancel once (expect "Cancelled"), then confirm with the fingerprint (expect "Erased 0 memories" and the desktop log unchanged otherwise). Finally add a new fingerprint in Settings and try again: expect a request to set up again.
7. Android 14 specifics to check: the `microphone` foreground service starts only from the visible app or the notification; `FOREGROUND_SERVICE_MICROPHONE` and `RECORD_AUDIO` are required; `BOOT_COMPLETED` cannot start it.

**iOS: external TestFlight (a colleague's iPhone)**
- Needs: an Apple Developer Program membership (paid; not authorised yet), an App Store Connect record, signing for the app and the widget extension, and a beta description with review information. The first external build of a version goes through Beta App Review. Builds expire after 90 days. Testers join by email invitation or public link, up to 10,000 per app.
- Plan, once approved: the owner enrols, then archives a Release build with the wake library embedded, uploads it, and invites one named tester by email (no public link). The tester runs a short silent checklist first (pairing, orb, Live Activity Stop), then the audible checks with the owner present.
- Step-up on that iPhone, after the App Attest entitlement is added: set up sensitive actions against `desktop_sim` with `NOTDOT_SIM_APPLE_APP=<team id>.<bundle id>` and the category the build reports (`NOTDOT_SIM_APPLE_CATEGORIES`; add `NOTDOT_SIM_APPLE_DEVELOPMENT=1` for an Xcode-installed build, which uses the development environment); expect `apple_app_attested`. Then erase once with Face ID, cancel once, and check a second erase advances the assertion counter (a replay is refused).
- Until then, iOS evidence is simulator-only.

## Native dependency note: libc and iOS

libc 0.2.190 stopped exposing `net/route.h` constants and `in6_ifreq` on iOS, but iroh's `netwatch` and `netdev` still use them there, so the mobile core does not compile for iOS with the desktop's libc 0.2.191. `mobile/rust` builds the app library with libc 0.2.189. `scripts/check_mobile_lock.py` (run in CI) fails if any other locked package differs from the desktop lock. Remove the split once libc or iroh fixes iOS.
